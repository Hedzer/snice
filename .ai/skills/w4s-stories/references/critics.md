# Advisory critics

Perform quick sanity checks using supplied research and decisions; apply only relevant checks, without repeating research or creating prolonged review cycles.
Critique the stories themselves; consult relevant design and research as supporting context.
Apply the binding technical-scope and accuracy-and-truth rules in the shared rules; flag unsupported factual claims and unnecessary implementation prescription.
Send advice and questions directly to the story writer, not the coordinator.
Give critics the user's request and clarifications, proposed stories, and supporting evidence; ask them to flag unsupported claims, invented requirements, misattributed decisions, and consequential unanswered questions.
Give each the applicable policies, settled decisions, and its instructions from this skill:

- A: [behaviour/contracts](critics/behaviour.md).
- B: [risk/integrity](critics/risk.md).
- C: [construction/proof](critics/quality.md).
- D: [following this skill](critics/skill-adherence.md).

Include the bundled [Safeloop guide](safeloop/guide.md) in A/B/C dispatches; each reads it in full and only the language follow-ups relevant to its review. Existing scope, advisory authority, and verification timing remain binding.

Include this explicit assignment in D's dispatch: "Read this skill in full and check that the author followed it; give brief advisory corrections within the agreed scope."

Run independent critics in parallel when supported.
Apply the questions to the available design: trace concrete scenarios and counterexamples.
Implementation tests, coverage, and executed customer evidence belong to implementation, not a story-authoring gate.
Derive concerns from this project; checklist examples do not create new requirements.
Critics may consult all supplied context; check that each story itself includes everything its eventual worker needs without the authoring conversation or linked design documents.

Critics advise only; they cannot invent requirements, expand scope, or block progress.
Report serious omissions, contradictions, missing branches, or supported risks with the affected requirement, evidence, consequence, and a focused question or bounded correction.
Attempt to refute the concern first.
No nitpicks, hypothetical feature requests, pass/fail matrices, vetoes, or approval loops.
The writer assesses advice against user intent and sends only unresolved user decisions through the coordinator.
Continue independent story-authoring work without waiting for critic completion or an all-clear.
Reuse unchanged advice; request an affected follow-up only when useful.
Save useful findings in the design, not a separate review bureaucracy.
